# rent3 화면 단순화 · 계약방 대화 체계화 구현 계획서 (개정 2판)

작성 2026-11-11 · 개정 2026-11-11(Gemini 검토 의견 + 코드 대조 반영, 11장 참고)
대상: 임대인 앱(`rent3_lessor`) · 임차인 앱(`rent3_tenant`) · 계약 앱(`rent3_contract`)

## 1. 목표

1. 각 앱의 첫 화면은 **그 사람이 매일 쓰는 한 가지**만 보여 준다. 나머지 기능은 모두 `☰ 메뉴` 안에서 들어간다.
   - 임대인: 월 임대료 수납 현황
   - 임차인: 내 월세 납부 확인
2. 계약 화면에서 임대인과 임차인의 **대화를 계약방 안으로 가져와**, 질문·수정 요청·제안이 단계와 항목에 묶여 남게 한다. 전화·카톡에 의존하지 않는다.
3. 같은 일을 하는 화면이 앱마다 다르게 생기지 않도록 **공통 틀**(머리글·메뉴·창·버튼 크기)을 하나로 만든다.

## 3. 설계 원칙

- **첫 화면 = 오늘 할 일 한 가지.** 알림이 있으면 맨 위에 배너(최대 2줄), 그 외는 메뉴.
- **메뉴는 층을 나눈다.** 업무(자주) / 관리(가끔) / 이동·도움말(거의 안 씀).
- **한 화면 한 목적.** 화면이 길어지면 섹션을 접지 말고 화면을 나눈다.
- **같은 설정은 한 곳에만 둔다.** 다른 메뉴에는 바로가기 버튼만 둔다.
- **모든 터치 영역은 40px 이상**, 본문 14px 이상. 금액·날짜 입력은 창(모달)에서 한다.
- **대화는 맥락에 붙인다.** 계약 단계·조건 항목·호실에 연결된 대화만 둔다(범용 채팅방 금지).
- **제약:** `core/`와 `run.py`는 한 줄도 수정하지 않는다(`test_01_immutable_core_zero_changes`). 모든 변경은 `apps/rent_dist/`, `shared_ui/`, `tests/`, `docs/` 안에서 한다.

## 4. 메뉴 체계 개편

### 4.1 임대인

첫 화면: **수납 현황**(호실 풀다운 + 수납내역·계약내용·만기통보·전출). 상단 탭 줄은 없애고 `☰ 메뉴` 하나만 둔다.

```
☰ 메뉴
 ├ 계약 · 매물
 │   직거래 계약 / 중개 계약서 사진 등록 / 임대매물 등록
 ├ 세무 · 경비                    ← 허브 화면(4.3)
 ├ 운영
 │   메시지(계약·입주자) / A/S 접수 / 일괄 납입 통보
 ├ 건물
 │   건물 정보 수정 / 부가세·소득세 대상 호실 설정   ← 이 설정 화면은 여기에만 둔다
 └ 도움말 · 이동
     이용 매뉴얼   (임차인 앱·관리인 앱·Data Pool 관제 링크는 일반 임대인에게 필요 없으므로 admin에게만 보인다)
```

- 요약 카드 4개는 **한 줄 띠**(미납 합계 강조 + 가동률)로 줄이고, 연간 수납액·NOI는 세무 화면으로 옮긴다.
- "그 밖의 안내"(D-3·D+1 일괄 통보)는 `운영 ▸ 일괄 납입 통보`로 옮긴다.
- **퇴실정산:** 호실 카드의 `전출` 창이 이미 정산·환불 문자·공실 전환까지 한다. 따라서 `운영`에서 퇴실정산 섹션은 **없애고**, 지난 정산 내역 조회가 필요하면 `전출` 창 안에 "지난 정산" 링크로 넣는다.

### 4.2 임차인

첫 화면: **내 월세 납부 확인**. `빈 집 찾기`와 나머지는 메뉴로 보낸다.

```
첫 화면
  [할 일 배너]  우선순위: 미납 통보 > 퇴실 정산 > 만기 확인 요청 (해당할 때만, 최대 2줄, 눌러서 상세)
  이번 달 납부 + 월별 납부 현황
  내 계약 요약(보증금·월세·만기일)
☰ 메뉴
  계약 · 서류: 직거래 계약 / 납부확인서(연말정산) / 중개 계약서 사본
  요청: A/S 요청 / 메시지
  찾기: 빈 집 찾기
  도움말
```

### 4.3 세무 허브

세금 화면을 4개 하위 화면으로 나눈다. 허브는 큰 버튼 4개, 연도 선택, "참고용 추정치" 안내만 둔다.

| 하위 화면 | 담는 것 |
|---|---|
| 종합소득세 | 소득 추정, 주택 분리과세 / 종합과세 구분, CSV |
| 부가세 | 1기·2기 자료, 매입세액. 대상 호실 설정은 `건물 ▸ 대상 호실 설정`으로 가는 **바로가기 버튼**만 둔다 |
| 세금계산서 | 발행 대장, 상태·승인번호 입력, 홈택스 CSV. **계약 시 세금계산서 발행 요청 여부, 공급받는자 사업자 정보·사업장 주소 입력·수정(주거용·기숙사 포함 전 호실)** 동선을 이 화면에서 잃지 않는다 |
| 경비 · 면세 신고 | 경비 등록·수정, 사업장현황신고 자료 |

### 4.4 관리인 앱 개편 · 대리 접속 일원화

**관리인의 업무는 둘이다.** (a) 가입 임대인 가맹 심사와 월 이용료(가맹비) 관리, (b) 사용법을 모르는 임대인·임차인을 대신해 해당 건물·호실·입장으로 접속해 돕는 원격 지원.

**원칙:** 건물·세입자·역할을 고르는 관리자용 선택기는 **관리인 앱 한 곳에만** 둔다. 임대인·임차인·계약 앱은 "지금 접속한(또는 URL로 지정된) 그 사람의 화면"만 그린다.

#### 관리인 앱 화면

```
관리인 앱
 ├ 🎯 원격 지원 · 대리 접속   (맨 위 고정 카드)
 │    1) 건물(지점) 선택
 │    2) 호실 선택  → 해당 호실의 임대인 · 현 임차인 · 진행 중 계약방이 자동으로 표시
 │    3) 입장 버튼
 │         [임대인 입장]  /rent3_lessor/?branch=<지점>&room=<호실>
 │         [임차인 입장]  /rent3_tenant/?tenant=<임차인 id>        (공실이면 비활성)
 │         [계약방 입장]  /rent3_contract/?session=<세션>&role=<lessor|tenant>   (진행 중 계약이 있을 때)
 └ 👑 가맹 임대인 심사 · 월 이용료 관리   (지금 기능 그대로: 승인·정지, 등기부 대조, 완납 정산, 비밀번호 임시 재설정)
```

- URL 파라미터: 임차인(`?tenant=`)과 임대인(`?branch=`)은 이미 있다. 임대인 앱의 **`room`** 은 새로 읽어야 하고(선택된 호실로 시작), 계약 앱의 `role`은 지금 `cosign` 계정에게만 인정되므로 **admin의 관전 모드**에서도 읽도록 바꾼다(파라미터 이름은 기존 `role`을 그대로 쓴다).
- 서버: 관리인 앱용 조회 API `GET /rent3_admin/support/directory?branch=`(호실별 임대인·현 임차인·진행 중 세션)와 접속 기록 API `POST /rent3_admin/support/enter`를 추가한다. 둘 다 admin 전용.
- admin 토큰이 모든 지점·임차인·세션을 이미 다룰 수 있으므로(`lessor_scope`, `tenant_scope`, `session_party_ok`) 토큰 재발급은 필요 없다.

#### 대리 접속 안전장치

1. **당사자 본인의 법적 행위는 대리할 수 없다.** admin 토큰으로는 휴대폰 본인인증, 신분증·등기부 확인 잠금, 옵션 점검 확인, 조건 동의(`agree_step3`), 전자서명(`sign_step4`), 체결 확정(`step5/complete`), 가맹 신청 본인인증을 서버가 거부(403)한다. 지금은 `contract_scope`가 admin이면 무조건 통과시키므로 **이 구멍을 먼저 막는다.** 계약방 대리 접속은 열람 전용이고 화면의 동의·서명 버튼은 비활성이다.
2. **금전·계약 기록은 읽기 전용이다. 임대인 본인이 한다(확정).** 임대인·임차인·계약 앱의 `POST` 요청은 admin 토큰으로는 **허용 목록**(지원 채팅 글쓰기, A/S 접수·배정)만 통과하고 나머지는 403이다. 허용 목록 방식이라 나중에 추가되는 기능도 기본이 "막힘"이다. 막히는 것의 예: 수납 입력·수정, 경비·계약 내용 수정, 호실 금액 설정, 대상 호실 설정, 세금계산서 상태 기록, 퇴실 정산, 도어락·출입 정보 교부·변경, 임차인의 납부·정산 동의·갱신 예고 확인. (관리인 앱 자체의 가맹 심사·이용료 정산은 별개이며 그대로다.) 대리 접속 화면에서는 해당 버튼을 숨기고 "관리인은 볼 수만 있습니다. 직접 처리해 주세요" 안내를 보인다.
3. **접속 기록을 남긴다.** URL 이동만으로는 흔적이 없으므로, 관리인 앱에서 입장할 때마다 접속 기록(누가·언제·건물·호실·입장·사유 분류·지원 채팅 id)을 `support/enter`로 남긴다. 풀 이벤트의 `actor` 기록은 이미 있다.
4. **화면 맨 위 띠:** admin이 대리 접속 중이면 공통 틀(`r3_shell.js`)이 `🛡️ 관리인 대리 접속 중(보기 전용): 시크빌 201호 (임차인 입장) [← 관리인 페이지로]` 띠를 모든 앱에 띄운다. 띠는 admin 세션일 때만 나온다. 사용자 쪽에는 "관리인이 접속 중입니다" 알림을 보인다.
5. **일반 사용자가 URL을 바꿔도 소용없다.** 임차인이 `?tenant=`를 다른 사람 id로 바꿔도 기존 `tenant_scope`가 403으로 막는다. 이 동작은 테스트로 고정한다.

#### 접속 사유: 지원 채팅으로 받는다

- **방식(확정):** 접속 사유는 별도 입력칸이 아니라 **관리인과 사용자의 지원 채팅**에서 주고받는다. 사용자가 `관리인에게 문의`(임대인·임차인 앱 메뉴)로 요청하거나 관리인이 먼저 채팅을 열 수 있다. 관리인 앱의 원격 지원 카드는 이 채팅 목록에서 대상을 고르고 `입장`을 누른다. 입장하면 그 채팅에 자동 기록("관리인이 임차인 입장으로 접속했습니다")이 남고 접속 기록과 연결된다. 채팅이 없는 호실에는 입장할 수 없다.
- **채팅 보관(확정):** 지원 채팅 글은 **10일** 뒤 삭제한다. 스케줄러가 없으므로(Coolify에 크론 없음) 서버 기동 시와 채팅 목록 조회 때 기한이 지난 글을 지우는 방식(지연 삭제)으로 한다.
- **접속 기록은 별개로 오래 보관한다.** 접속 기록은 글이 아니라 "누가·언제·어디·어떤 입장·사유 분류"만 담는다. 사유 분류는 고정 목록(사용법 문의 / 오류 신고 / 계정 문제 / 기타)이라 개인정보가 거의 없다. 채팅이 지워져도 "접속했다는 사실"은 남아야 개인정보 열람 이력을 확인할 수 있다. 보관 기간은 **1년 이상**을 기본으로 하되 법무 확인이 필요하다.
- **이벤트 로그 주의:** 지원 채팅 글의 풀 이벤트 요약에는 **본문을 넣지 않는다**(예: "지원 채팅 [201호] 이름"만). 기존 `DirectChat`의 요약(앞 24자)도 같은 이유로 본문을 빼도록 고친다. 안 그러면 채팅을 지워도 `_events.jsonl`에 본문이 남는다.
- **전화로 도움을 요청한 경우(확정):** 채팅조차 어려운 분들이 전화로 요청하는 경우가 많으므로, 원격 지원에 동의한 사용자에 한해 **두 경로**를 모두 허용한다.
  - (a) 사용자가 먼저 남긴 지원 채팅을 골라 입장한다.
  - (b) 관리인이 원격 지원 카드에서 **사유 분류**(사용법 문의 등)와 **전화 접수 메모**를 입력하면, 해당 호실 지원 채팅에 `[전화 요청 접수] ...` 메시지가 **자동 생성**되고 그대로 입장할 수 있다. 전화로 시작해도 사용자에게 채팅 기록과 입장 사실이 똑같이 남는다. (전화 접수 메모도 채팅 글이므로 10일 뒤 삭제된다.)
  - 두 경로 모두 원격 지원 허용이 켜져 있어야 하고, 꺼져 있으면 입장 버튼이 비활성이며 서버도 거부한다.

#### 가입 동의 · 개인정보 (신규)

- **가입 화면(`/auth/register`, 포털 회원가입 탭)에 동의 절차를 넣는다.** 항목을 나누어 각각 체크한다(한꺼번에 묶는 포괄 동의 금지).
  1. (필수) 개인정보 수집·이용 동의 — 수집 항목, 이용 목적, 보유 기간, 거부 권리와 불이익, [전문 보기]
  2. (선택) **관리인 원격 지원 접속 동의** — 요청하신 문의에 한해 관리인이 보기 전용으로 접속하며, 금전·계약 기록은 수정할 수 없고, 접속 기록이 남는다는 설명
  3. 안내(체크 없음): 등기부 AI 읽기는 사용하는 시점에 별도 동의를 받는다(이미 있음). 이때 Google Gemini로 전송된다는 점, 국외 이전에 해당할 수 있다는 점을 안내 문구에 넣는다.
- **원격 지원 동의는 선택으로 둔다.** 서비스 이용에 꼭 필요한 항목이 아니므로 필수로 묶으면 안 될 수 있다. 동의하지 않은 사용자의 호실은 관리인 앱에서 `입장`이 비활성이고, 전화 안내로 돕는다. 서버(`support/enter`)도 동의 여부를 검사한다.
- **언제든 ON/OFF(확정):** 처음에 동의하지 않았더라도 임대인·임차인 앱 메뉴 `🛡️ 원격 지원 허용 설정`에서 언제든 켜고 끌 수 있다. 도움이 필요해진 시점에 사용자가 직접 켜면 된다. 끄면 이후 입장할 수 없다.
- **동의 기록:** 사용자 레코드에 동의 버전과 일시를 저장한다(`consents`: 개인정보 처리방침 버전·동의 일시, 원격 지원 동의 여부·일시). 약관 문구가 바뀌면 버전을 올려 다시 받는다.
- **기존 사용자 재동의:** 장부로 옮긴 임차인 63명, 부트스트랩으로 만든 임대인 3명, 이미 가입한 사용자는 동의 기록이 없다. 로그인했을 때 동의 기록이 없으면 토큰을 주지 않고 `동의 필요` 응답과 단기 확인표를 돌려주며, 동의 화면에서 동의하면 로그인이 이어지게 한다.
- **처리방침 문서:** `/rent3/privacy.html`을 만든다. 수집 항목(이름·연락처·생년월일 앞 6자리·계좌·차량번호·사업자 정보 등), 목적, 보유 기간, 위탁·국외 이전(서버 사업자, Google Gemini), 파기 방법, 열람·정정·삭제 요청 방법, 문의처를 담는다. **초안은 제가 쓰지만 법무 검토 후에 적용한다.**

## 5. 계약방 대화 체계화

### 5.1 대화 종류와 조건 변경 규칙

사람이 쓰는 것 셋과 자동 기록 하나, 네 종류로만 나눈다.

| 종류 | 용도 | 예 |
|---|---|---|
| 문의 | 자유 질문(짧게) | "관리비에 인터넷 포함인가요?" |
| 제안 | **숫자·날짜 6개 항목**을 직접 제시, 상대가 수락·거절 | 계약금 30만 → 50만 (항목: 보증금·계약금·월세·관리비·입주일·계약기간) |
| 수정 요청 | 문구 협의가 필요한 항목. 받는 쪽이 직접 고쳐서 다시 제시 | 특약 사항 문구 |
| 시스템 | 자동 기록 | "임차인이 등기부 확인을 마쳤습니다" |

**제안을 수락하면 반드시 기존 `CoSignSession.update_terms()`를 호출한다.** 별도 코드로 `terms`를 덮어쓰지 않는다. 이 함수는 다음을 함께 처리한다.

- `revision` 1 증가, 양측 Step 3 동의 초기화, 양측 서명·무결성 해시 초기화
- 단계가 4 이상이면 3으로 되돌림
- 근저당·보증보험 필수 특약 자동 재반영
- 재계약(`RENEWAL`)이면 5% 상한 검증(실패하면 수락이 거절되고 제안은 열린 채 남는다)

추가 규칙:

1. **열린 제안·수정 요청이 하나라도 있으면 Step 3 최종 동의를 막는다.** 화면에서 버튼을 숨기는 것만으로 부족하므로 서버 `agree_step3()`에도 같은 검사를 넣는다(`cosign.py`는 `core/`가 아니므로 수정 가능).
2. **제안·수정 요청은 단계 ③까지만 만들 수 있다.** 단계 ④(서명) 이후에는 문의만 가능하다. 조건을 바꿔야 하면 기존 "조건 수정" 경로로 가며, 서명이 초기화된다는 경고를 먼저 보여 준다.
3. 수락 기록은 `update_terms`의 `role`에 **수락한 쪽**을 넘기고, 메시지 id를 같이 기록한다.
4. 제안 작성자는 자기 제안을 철회할 수 있다(철회 시 `status=withdrawn`).

### 5.2 화면

1. 계약 화면 맨 위에 **한 줄 상태**: "지금 내 차례: 옵션 점검표 확인" / "상대 차례: 임대인이 조건을 확인 중".
   - 단계별 임대인·임차인 완료·대기 배지 4개를 **두 점(🟢 임대인 · 🟢 임차인)** 으로 통일한다.
2. 오른쪽 아래에 `💬` 버튼(안 읽은 수 배지). 누르면 아래에서 올라오는 대화창이 열린다.
3. **단계 ③ 조건 화면:** 현재 조건을 그대로 보여 주고, 바꾸고 싶은 항목 옆에만 `제안`(6개 항목) 또는 `수정 요청`(특약)을 둔다. 맨 아래에 **`계약 조건 전체 동의` 버튼 하나**로 단계를 마친다. 항목별 동의 버튼과 서버의 항목별 동의 상태는 만들지 않는다.
4. 대화창 맨 아래 **빠른 답변 버튼**: `확인했습니다` · `나중에 얘기해요`. 글을 직접 쓰는 것은 문의 때만.
5. 호출(call) 단계는 **초대 문자 복사 + QR** 하나로 줄이고, 응답 화면 문구를 짧게 한다.

### 5.3 데이터와 API

**저장소:** 새 컬렉션을 만들지 않는다. `POOL_COLLECTIONS`는 8개 고정이며 `DirectChat`·`TaxInvoiceRecord`·`MaintenanceTicket`이 모두 `ops` 컬렉션을 쓴다. 대화도 `ops`에 둔다.

**모델:** 새 `ContractMessage`를 만들지 않고 **기존 `DirectChat`을 확장**한다(선택 필드 추가). 단, 관리인 **지원 채팅은 `DirectChat`이 아니라 별도 `SupportMessage`** 로 만들었다(4A-3). `DirectChat`은 임대인 대시보드와 임차인 마이홈이 호실·지점 기준으로 통째로 읽어 가므로, 같은 모델에 섞으면 한 사람의 지원 요청이 상대방 화면에 보일 수 있기 때문이다.

```
기존: id, branch, id_room, room_no, sender_role, sender_name, message, is_read, created_at ...
추가: session_id(계약방, 없으면 입주 후 대화), tenant_id(없을 수 있음),
      kind(chat|question|proposal|change_request|system),
      step(1~5), field(조건 항목 이름),
      proposal{field, old, new}, status(open|accepted|declined|withdrawn)
```

- 호출 단계에서는 임차인이 아직 `Tenant`로 등록되기 전일 수 있다(예비 임차인). 그래서 대화의 키는 `session_id`이고 `tenant_id`는 비어 있어도 된다.
- 한 모델이라서 5.4의 "체결 후 같은 호실 대화로 이어 보기"에 합치기·정렬 코드가 필요 없다. 입주 후 대화 화면은 `kind in (chat, system)`만 보여 협상 기록이 섞이지 않게 한다.

| API | 동작 |
|---|---|
| `GET /sessions/{id}/messages` | 당사자만 조회 |
| `POST /sessions/{id}/messages` | 문의·제안·수정 요청 작성 (제안·수정 요청은 단계 ③까지) |
| `POST /messages/{id}/respond` | 수락·거절·철회 (수락 시 `update_terms` 호출) |
| `POST /sessions/{id}/messages/read` | 읽음 처리 |

- 접근 제한: 계약 당사자(임대인 지점, 임차인 본인)만. 다른 지점·다른 임차인은 403. 기존 `session_party_ok`를 그대로 쓴다.
- 갱신은 기존 `pool_revision` 폴링을 쓴다. 푸시는 2차.

### 5.4 보관과 입주 후 대화 통합

- **체결 후 읽기 전용 보관.** 체결 시점의 대화 목록을 SHA-256 해시로 만들어 `Contract`에 한 줄(`chat_digest`) 기록한다. 분쟁 때 변조 여부를 확인할 수 있다.
- **보관 기간(확정):** 체결된 계약의 대화는 **계약 종료(퇴실 완료) 후 5년**, 체결되지 못하고 취소(`CANCELLED`)된 세션의 대화는 **90일** 보관한다.
  - 1차 구현 범위는 "체결 후 읽기 전용 보관 + `chat_digest` 기록"까지다. 기간이 지난 대화의 자동 삭제는 후속 작업으로 둔다(삭제 작업을 만들 때 위 기간을 기준으로 한다).
- **메시지 메뉴 하나로 통합.** 임대인 `ops`의 인앱 메신저와 임차인 마이홈 대화를 메뉴 `메시지`로 모아 **호실별 대화 목록**으로 보여 준다.
- 임대인이 임차인에게 보내는 수납·미납 안내문은 지금처럼 **복사 → 외부 문자**를 유지한다.

## 8. 검증 기준

- **화면:** 360px 폭에서 첫 화면이 스크롤 없이 핵심 정보(임대인은 선택한 호실 카드, 임차인은 이번 달 납부)를 보여 준다. 모든 버튼 40px 이상.
- **메뉴:** 기존 기능이 모두 메뉴에서 도달 가능하다(빠진 기능 0개). 메뉴 목록은 테스트로 고정한다.
- **권한:** 다른 지점 임대인, 다른 임차인이 대화·제안에 접근하면 403.
- **조건 변경:**
  - 제안 수락 전에는 `terms`가 바뀌지 않는다.
  - 수락 시 `revision`이 오르고 양측 동의·서명이 초기화되며, 5% 상한 같은 기존 검증을 통과해야 반영된다.
  - 열린 제안이 있으면 서버가 Step 3 동의를 거부한다.
  - 단계 ④ 이후에는 제안 작성이 거부된다.
- **기존 테스트 호환:** `test_43_frontends_do_not_call_staff_only_apis_as_tenant`가 `rent3_tenant/frontend/app.js`에서 `const isTenantUser`와 `if (!tenantList.length && !isTenantUser) await loadTenants();` 문자열을 직접 검사한다. 4단계에서 이 구문을 지우거나 바꾸지 않는다. `test_01`(코어 무변경)도 항상 통과해야 한다.
- **대리 접속(4A):**
  - admin 토큰으로 본인인증·동의·서명·체결 요청을 보내면 403이다(역할 값과 무관).
  - 임차인·임대인 토큰으로는 다른 사람의 `?tenant=`·`?branch=`·세션에 접근하면 403이다.
  - 대리 접속 띠는 admin 세션에서만 보이고, 관리인 페이지로 돌아가는 링크가 동작한다.
  - 진입할 때마다 접속 기록이 남는다.
  - admin 토큰으로 허용 목록 밖의 `POST`(수납·계약·경비·정산 등)는 403이고, 허용 목록(지원 채팅·A/S)은 통과한다.
  - 동의하지 않은 사용자 호실에는 `support/enter`가 거부된다. 지원 채팅이 없는 호실도 거부된다.
  - 지원 채팅 글은 10일이 지나면 목록 조회 때 사라지고, 풀 이벤트 요약에 본문이 없다. 접속 기록은 남는다.
  - 동의 기록이 없는 사용자는 로그인 때 `동의 필요` 응답을 받고, 동의 후 로그인된다. 개인정보 동의 없이는 가입이 안 된다.
  - **시험 영향:** 시험의 기본 요청이 admin 토큰이고, 서명·동의 흐름과 금전·계약 기록 호출이 시험 안에 100곳 가까이 있다. 두 방법 중 고른다.
    - (a) 당사자 토큰(임대인·임차인)으로 바꾼다. 정확하지만 작업이 크다.
    - (b) 서버에 `RENT3_ADMIN_PROXY_STRICT`(기본 켜짐) 스위치를 두고, 기존 시험 묶음은 끄고 돌리며, 엄격 모드는 전용 시험에서 켜서 검사한다. 작업은 작지만 엄격 모드에서는 나머지 흐름이 시험되지 않는다.
    - 권장: (b)로 시작하고, 고치는 시험부터 (a)로 옮긴다. 운영 서버는 스위치를 켠 채(기본값)로 둔다. 시연·E2E 스크립트(`scripts/e2e_pair/play.py` 등)도 점검 대상이다.
- **회귀:** `tests.test_rent3_pool_suite` 전체 통과 + 신규 대화 테스트 + 휴대폰 크기 화면 확인 스크립트(`scripts/e2e_pair/phone_*.mjs`)로 눈으로 확인.

**남은 결정**

1. **관리인의 직접 열람 범위.** 지금 서버는 **입장 절차(원격 지원 허용 + 채팅 + 접속 기록)를 거치지 않은 admin 토큰의 읽기(GET)는 막지 않는다.** 관리 업무상 필요한 관리인 API·Data Pool 탐색기가 있기 때문이다. 관리인 앱에서 임대인·임차인 화면으로 가는 링크는 없앴지만, 관리인이 주소를 직접 쳐서 열면 열린다. 읽기까지 입장 절차를 강제하려면 admin 토큰의 임대인·임차인·계약 앱 GET에도 같은 조건을 거는 별도 작업이 필요하다.
2. **운영 배포 전 확인 목록(법무 검토 때 함께):** 처리방침의 수탁자·국외 이전(Google Gemini)·담당자 연락처 기재, 계약·수납 기록 법정 보존 기간.

| `BASS_SECRET` | 고정값 | 비워 두면 서버를 다시 띄울 때마다 로그인 토큰이 모두 무효가 된다 |
| `RENT3_DEMO_LOGIN` | `0` | 시연 로그인(1212 등) 끄기 |
| `RENT3_FAKE_IDENTITY` | 끔 | 실제 본인인증 연동 전까지는 운영 노출 범위를 정해서 사용 |
| `RENT3_BOOTSTRAP_CONFIG`와 File Mount | 사용 후 삭제 | 비밀번호·개인정보가 든 파일이 서버에 남지 않게 |

### A-2. 가입·첫 로그인 동의
- `privacy.html`의 운영 상호·개인정보 보호책임자·수탁사·국외 이전(Google Gemini)·접속기록 보관 기간을 법무 검토 후 확정한다.
- 기존 임대인 3명·임차인(장부 이관 63명)은 첫 로그인 때 동의 팝업이 뜬다. **이관 임차인은 로그인 비밀번호가 없으므로 비밀번호 재설정부터** 안내한다.
- 이미 로그인된 토큰은 만료될 때까지 동의 없이도 쓰인다(다음 로그인부터 적용).
- `☰ ▸ 🛡️ 원격 지원 허용 설정`에서 ON/OFF가 바로 바뀌는지 확인한다.

### A-3. 관리인 원격 지원
1. 사용자가 `☰ ▸ 💬 관리인에게 문의`로 글을 남기거나, 관리인이 관리인 앱에서 `전화 접수`를 남긴다(사용자의 원격 지원 허용이 ON이어야 입장 가능).
2. 관리인 앱 `원격 지원 · 대리 접속`에서 입장 → 주황색 대리 접속 띠, 사용자 화면 접속 알림 확인.
3. 대리 접속 중 수납·계약·경비 저장이 막히는지(403 안내) 확인.
- 알려진 한계: 관리인이 주소를 직접 입력해 읽는 것은 서버가 막지 않는다(후순위). 지원 채팅은 10일 뒤, 접속 기록은 1년 뒤 정리되나 **자동 삭제는 지원 API·로그인 때 지연 삭제**로 동작한다.

### A-4. 공동계약 협상 · 체결 봉인
1. 3단계에서 제안 → 상대 수락(임차인은 본인인증 필요) → 리비전 증가·동의 초기화 → 열린 제안·수정 요청이 없을 때만 `계약 조건 전체 동의`가 켜진다.
2. 서명 이후 조건 변경은 `조건 다시 열기`만 가능(서명 초기화·3단계 복귀).
3. 체결 후 계약서 화면의 `협상 대화 기록 해시`와, `☰ ▸ 메시지 ▸ 계약 협상 기록`의 `✅ 일치` 표시를 확인한다.

### A-4-2. 대화 보관 기간(지연 삭제)
- 취소된 계약방: 취소 시각(`cancelled_at`, 없으면 `updated_at`)으로부터 **90일을 넘기면** 삭제. 진행 중인 계약방은 삭제하지 않는다.
- 체결된 계약: 계약이 `ACTIVE`인 동안은 절대 삭제하지 않고, 종료 확정일(`ended_at` → `move_out_date` → `updated_at`) 후 **5년(1,825일)을 넘기면** 삭제. 재계약으로 마감(`RENEWED`)된 계약도 같은 기준.
- 삭제되면 `Contract.chat_purged_at`(취소 세션은 `CoSignSession.chat_purged_at`)을 남긴다. 화면·API는 이를 **변조(⚠️ 해시 달라짐)와 구분**해 "보관 기간이 지나 삭제되었습니다. 체결 당시 해시만 남아 있습니다"로 보여 준다(`purged: true`, `digest_ok: null`).
- 실행: 로그인, 계약방 대화 조회, 임대인·임차인 메시지 조회 때 지연 삭제. 조회가 잦으므로 **10분에 한 번만 실제로 훑는다**.
- 운영 점검: 오래된 계약이 아직 없어 첫 삭제는 한참 뒤에 일어난다. 경과일 기준을 바꾸려면 `contract_chat.CANCELLED_RETENTION_DAYS`·`CONCLUDED_RETENTION_DAYS`를 고친다.

### A-5. 아직 구현하지 않은 것
관리인의 직접 읽기(GET) 제한, 계약 앱 단계 ①②의 완료/대기 배지 정리, QA 체크리스트 PDF·계약 앱 이용 매뉴얼의 옛 3단계 표현 정리.

14판(2026-11-12): 대화 보관 기간 지연 삭제 구현(`contract_chat.purge_expired`). 알아 둘 점:

- 계약 종료 시각 기준을 위해 `Contract.ended_at`을 새로 두었다(퇴실·해지 `terminate()`와 재계약 마감 `RENEWED`에서 기록). 값이 비어 있는 옛 계약은 `move_out_date` → `updated_at` 순으로 대신 쓴다.
- 기간 경계는 "넘기면 삭제"다(정확히 90일째·1,825일째는 보존).
- 삭제 기록(풀 이벤트)에는 본문이 남지 않는다. 남는 것은 체결 시점의 해시와 글 수(`chat_digest_count`)뿐이다.
- 보관 중 누군가 대화를 지우면(삭제 표시 없이 글 수가 줄면) 이전처럼 변조(⚠️)로 보인다.
