# rent3 화면 단순화 · 계약방 대화 체계화 구현 계획서 (개정 2판)

작성 2026-11-11 · 개정 2026-11-11(Gemini 검토 의견 + 코드 대조 반영, 11장 참고)
대상: 임대인 앱(`rent3_lessor`) · 임차인 앱(`rent3_tenant`) · 계약 앱(`rent3_contract`)

## 1. 목표

1. 각 앱의 첫 화면은 **그 사람이 매일 쓰는 한 가지**만 보여 준다. 나머지 기능은 모두 `☰ 메뉴` 안에서 들어간다.
   - 임대인: 월 임대료 수납 현황
   - 임차인: 내 월세 납부 확인
2. 계약 화면에서 임대인과 임차인의 **대화를 계약방 안으로 가져와**, 질문·수정 요청·제안이 단계와 항목에 묶여 남게 한다. 전화·카톡에 의존하지 않는다.
3. 같은 일을 하는 화면이 앱마다 다르게 생기지 않도록 **공통 틀**(머리글·메뉴·창·버튼 크기)을 하나로 만든다.

## 3. 설계 원칙

- **첫 화면 = 오늘 할 일 한 가지.** 알림이 있으면 맨 위에 배너(최대 2줄), 그 외는 메뉴.
- **메뉴는 층을 나눈다.** 업무(자주) / 관리(가끔) / 이동·도움말(거의 안 씀).
- **한 화면 한 목적.** 화면이 길어지면 섹션을 접지 말고 화면을 나눈다.
- **같은 설정은 한 곳에만 둔다.** 다른 메뉴에는 바로가기 버튼만 둔다.
- **모든 터치 영역은 40px 이상**, 본문 14px 이상. 금액·날짜 입력은 창(모달)에서 한다.
- **대화는 맥락에 붙인다.** 계약 단계·조건 항목·호실에 연결된 대화만 둔다(범용 채팅방 금지).
- **제약:** `core/`와 `run.py`는 한 줄도 수정하지 않는다(`test_01_immutable_core_zero_changes`). 모든 변경은 `apps/rent_dist/`, `shared_ui/`, `tests/`, `docs/` 안에서 한다.

## 4. 메뉴 체계 개편

### 4.1 임대인

첫 화면: **수납 현황**(호실 풀다운 + 수납내역·계약내용·만기통보·전출). 상단 탭 줄은 없애고 `☰ 메뉴` 하나만 둔다.

```
☰ 메뉴
 ├ 계약 · 매물
 │   직거래 계약 / 중개 계약서 사진 등록 / 임대매물 등록
 ├ 세무 · 경비                    ← 허브 화면(4.3)
 ├ 운영
 │   메시지(계약·입주자) / A/S 접수 / 일괄 납입 통보
 ├ 건물
 │   건물 정보 수정 / 부가세·소득세 대상 호실 설정   ← 이 설정 화면은 여기에만 둔다
 └ 도움말 · 이동
     이용 매뉴얼 / 임차인 앱 / 관리인 앱 / Data Pool 관제
```

- 요약 카드 4개는 **한 줄 띠**(미납 합계 강조 + 가동률)로 줄이고, 연간 수납액·NOI는 세무 화면으로 옮긴다.
- "그 밖의 안내"(D-3·D+1 일괄 통보)는 `운영 ▸ 일괄 납입 통보`로 옮긴다.
- **퇴실정산:** 호실 카드의 `전출` 창이 이미 정산·환불 문자·공실 전환까지 한다. 따라서 `운영`에서 퇴실정산 섹션은 **없애고**, 지난 정산 내역 조회가 필요하면 `전출` 창 안에 "지난 정산" 링크로 넣는다.

### 4.2 임차인

첫 화면: **내 월세 납부 확인**. `빈 집 찾기`와 나머지는 메뉴로 보낸다.

```
첫 화면
  [할 일 배너]  우선순위: 미납 통보 > 퇴실 정산 > 만기 확인 요청 (해당할 때만, 최대 2줄, 눌러서 상세)
  이번 달 납부 + 월별 납부 현황
  내 계약 요약(보증금·월세·만기일)
☰ 메뉴
  계약 · 서류: 직거래 계약 / 납부확인서(연말정산) / 중개 계약서 사본
  요청: A/S 요청 / 메시지
  찾기: 빈 집 찾기
  도움말
```

### 4.3 세무 허브

세금 화면을 4개 하위 화면으로 나눈다. 허브는 큰 버튼 4개, 연도 선택, "참고용 추정치" 안내만 둔다.

| 하위 화면 | 담는 것 |
|---|---|
| 종합소득세 | 소득 추정, 주택 분리과세 / 종합과세 구분, CSV |
| 부가세 | 1기·2기 자료, 매입세액. 대상 호실 설정은 `건물 ▸ 대상 호실 설정`으로 가는 **바로가기 버튼**만 둔다 |
| 세금계산서 | 발행 대장, 상태·승인번호 입력, 홈택스 CSV. **계약 시 세금계산서 발행 요청 여부, 공급받는자 사업자 정보·사업장 주소 입력·수정(주거용·기숙사 포함 전 호실)** 동선을 이 화면에서 잃지 않는다 |
| 경비 · 면세 신고 | 경비 등록·수정, 사업장현황신고 자료 |

## 5. 계약방 대화 체계화

### 5.1 대화 종류와 조건 변경 규칙

사람이 쓰는 것 셋과 자동 기록 하나, 네 종류로만 나눈다.

| 종류 | 용도 | 예 |
|---|---|---|
| 문의 | 자유 질문(짧게) | "관리비에 인터넷 포함인가요?" |
| 제안 | **숫자·날짜 6개 항목**을 직접 제시, 상대가 수락·거절 | 계약금 30만 → 50만 (항목: 보증금·계약금·월세·관리비·입주일·계약기간) |
| 수정 요청 | 문구 협의가 필요한 항목. 받는 쪽이 직접 고쳐서 다시 제시 | 특약 사항 문구 |
| 시스템 | 자동 기록 | "임차인이 등기부 확인을 마쳤습니다" |

**제안을 수락하면 반드시 기존 `CoSignSession.update_terms()`를 호출한다.** 별도 코드로 `terms`를 덮어쓰지 않는다. 이 함수는 다음을 함께 처리한다.

- `revision` 1 증가, 양측 Step 3 동의 초기화, 양측 서명·무결성 해시 초기화
- 단계가 4 이상이면 3으로 되돌림
- 근저당·보증보험 필수 특약 자동 재반영
- 재계약(`RENEWAL`)이면 5% 상한 검증(실패하면 수락이 거절되고 제안은 열린 채 남는다)

추가 규칙:

1. **열린 제안·수정 요청이 하나라도 있으면 Step 3 최종 동의를 막는다.** 화면에서 버튼을 숨기는 것만으로 부족하므로 서버 `agree_step3()`에도 같은 검사를 넣는다(`cosign.py`는 `core/`가 아니므로 수정 가능).
2. **제안·수정 요청은 단계 ③까지만 만들 수 있다.** 단계 ④(서명) 이후에는 문의만 가능하다. 조건을 바꿔야 하면 기존 "조건 수정" 경로로 가며, 서명이 초기화된다는 경고를 먼저 보여 준다.
3. 수락 기록은 `update_terms`의 `role`에 **수락한 쪽**을 넘기고, 메시지 id를 같이 기록한다.
4. 제안 작성자는 자기 제안을 철회할 수 있다(철회 시 `status=withdrawn`).

### 5.2 화면

1. 계약 화면 맨 위에 **한 줄 상태**: "지금 내 차례: 옵션 점검표 확인" / "상대 차례: 임대인이 조건을 확인 중".
   - 단계별 임대인·임차인 완료·대기 배지 4개를 **두 점(🟢 임대인 · 🟢 임차인)** 으로 통일한다.
2. 오른쪽 아래에 `💬` 버튼(안 읽은 수 배지). 누르면 아래에서 올라오는 대화창이 열린다.
3. **단계 ③ 조건 화면:** 현재 조건을 그대로 보여 주고, 바꾸고 싶은 항목 옆에만 `제안`(6개 항목) 또는 `수정 요청`(특약)을 둔다. 맨 아래에 **`계약 조건 전체 동의` 버튼 하나**로 단계를 마친다. 항목별 동의 버튼과 서버의 항목별 동의 상태는 만들지 않는다.
4. 대화창 맨 아래 **빠른 답변 버튼**: `확인했습니다` · `나중에 얘기해요`. 글을 직접 쓰는 것은 문의 때만.
5. 호출(call) 단계는 **초대 문자 복사 + QR** 하나로 줄이고, 응답 화면 문구를 짧게 한다.

### 5.3 데이터와 API

**저장소:** 새 컬렉션을 만들지 않는다. `POOL_COLLECTIONS`는 8개 고정이며 `DirectChat`·`TaxInvoiceRecord`·`MaintenanceTicket`이 모두 `ops` 컬렉션을 쓴다. 대화도 `ops`에 둔다.

**모델:** 새 `ContractMessage`를 만들지 않고 **기존 `DirectChat`을 확장**한다(선택 필드 추가).

```
기존: id, branch, id_room, room_no, sender_role, sender_name, message, is_read, created_at ...
추가: session_id(계약방, 없으면 입주 후 대화), tenant_id(없을 수 있음),
      kind(chat|question|proposal|change_request|system),
      step(1~5), field(조건 항목 이름),
      proposal{field, old, new}, status(open|accepted|declined|withdrawn)
```

- 호출 단계에서는 임차인이 아직 `Tenant`로 등록되기 전일 수 있다(예비 임차인). 그래서 대화의 키는 `session_id`이고 `tenant_id`는 비어 있어도 된다.
- 한 모델이라서 5.4의 "체결 후 같은 호실 대화로 이어 보기"에 합치기·정렬 코드가 필요 없다. 입주 후 대화 화면은 `kind in (chat, system)`만 보여 협상 기록이 섞이지 않게 한다.

| API | 동작 |
|---|---|
| `GET /sessions/{id}/messages` | 당사자만 조회 |
| `POST /sessions/{id}/messages` | 문의·제안·수정 요청 작성 (제안·수정 요청은 단계 ③까지) |
| `POST /messages/{id}/respond` | 수락·거절·철회 (수락 시 `update_terms` 호출) |
| `POST /sessions/{id}/messages/read` | 읽음 처리 |

- 접근 제한: 계약 당사자(임대인 지점, 임차인 본인)만. 다른 지점·다른 임차인은 403. 기존 `session_party_ok`를 그대로 쓴다.
- 갱신은 기존 `pool_revision` 폴링을 쓴다. 푸시는 2차.

### 5.4 보관과 입주 후 대화 통합

- **체결 후 읽기 전용 보관.** 체결 시점의 대화 목록을 SHA-256 해시로 만들어 `Contract`에 한 줄(`chat_digest`) 기록한다. 분쟁 때 변조 여부를 확인할 수 있다.
- **보관 기간(확정):** 체결된 계약의 대화는 **계약 종료(퇴실 완료) 후 5년**, 체결되지 못하고 취소(`CANCELLED`)된 세션의 대화는 **90일** 보관한다.
  - 1차 구현 범위는 "체결 후 읽기 전용 보관 + `chat_digest` 기록"까지다. 기간이 지난 대화의 자동 삭제는 후속 작업으로 둔다(삭제 작업을 만들 때 위 기간을 기준으로 한다).
- **메시지 메뉴 하나로 통합.** 임대인 `ops`의 인앱 메신저와 임차인 마이홈 대화를 메뉴 `메시지`로 모아 **호실별 대화 목록**으로 보여 준다.
- 임대인이 임차인에게 보내는 수납·미납 안내문은 지금처럼 **복사 → 외부 문자**를 유지한다.

## 6. 공통 틀

- 디스크 경로 `shared_ui/r3_shell.js`, `shared_ui/r3_modal.js` → 브라우저 URL `/shared/ui/r3_shell.js`, `/shared/ui/r3_modal.js`. (`core/gateway.py`가 `shared_ui/`를 `/shared/ui`로 마운트한다.)
- `r3_shell.js`: 머리글(건물명[아이디] + 시각, 메뉴 버튼), 메뉴 서랍, 알림 배너.
- `r3_modal.js`: 지금 임대인 앱 안에 있는 창(모달) 코드를 꺼내 공용으로. 계약 앱의 단계 모달과 다이얼로그도 점차 맞춘다.
- **스타일은 공통 파일에 둔다.** 최근 `index.html`의 스타일이 빠져 화면이 깨진 일이 있었으므로, 스타일을 `index.html`에 두지 않고 공통 `.js`/`.css`에서 불러온다(임대인 앱은 현재 `app.js`가 직접 주입 중).

## 7. 단계별 진행

크기는 S(반나절 이내) / M(1~2일) / L(3일 이상)의 감각 단위입니다.

| 단계 | 내용 | 크기 | 위험 |
|---|---|---|---|
| 0 | **캐시 진단**: 배포 서버 응답 헤더(`Cache-Control`)와 앞단 프록시 확인, 재현 시도. 원인이 확인되면 그에 맞춰 처리. 안 되면 빌드 번호 쿼리(`app.js?v=`)로 보강 | S | 낮음 |
| 1 | 공통 틀 추출(`r3_shell`, `r3_modal`), 임대인 앱에 먼저 적용 | M | 중간 — 기존 화면 회귀 |

| 3 | 세무 허브 분리(4개 하위 화면), 대상 호실 설정은 건물 메뉴 한 곳 | M | 낮음 |
| 4 | 임차인 앱: 첫 화면 정리, 할 일 배너, 메뉴 개편 (`test_43` 가드 문자열 유지) | M | 낮음 |

권장 순서는 0 → 1 → 2 → 4 → 3 → 5 → 6 → 7입니다. 1~4단계는 배치만 바꾸므로 기존 기능이 그대로인지 확인하기 쉽습니다. 5~6단계는 계약 흐름이 바뀌므로 따로 큰 검증을 거칩니다.

## 8. 검증 기준

- **화면:** 360px 폭에서 첫 화면이 스크롤 없이 핵심 정보(임대인은 선택한 호실 카드, 임차인은 이번 달 납부)를 보여 준다. 모든 버튼 40px 이상.
- **메뉴:** 기존 기능이 모두 메뉴에서 도달 가능하다(빠진 기능 0개). 메뉴 목록은 테스트로 고정한다.
- **권한:** 다른 지점 임대인, 다른 임차인이 대화·제안에 접근하면 403.
- **조건 변경:**
  - 제안 수락 전에는 `terms`가 바뀌지 않는다.
  - 수락 시 `revision`이 오르고 양측 동의·서명이 초기화되며, 5% 상한 같은 기존 검증을 통과해야 반영된다.
  - 열린 제안이 있으면 서버가 Step 3 동의를 거부한다.
  - 단계 ④ 이후에는 제안 작성이 거부된다.
- **기존 테스트 호환:** `test_43_frontends_do_not_call_staff_only_apis_as_tenant`가 `rent3_tenant/frontend/app.js`에서 `const isTenantUser`와 `if (!tenantList.length && !isTenantUser) await loadTenants();` 문자열을 직접 검사한다. 4단계에서 이 구문을 지우거나 바꾸지 않는다. `test_01`(코어 무변경)도 항상 통과해야 한다.
- **회귀:** `tests.test_rent3_pool_suite` 전체 통과 + 신규 대화 테스트 + 휴대폰 크기 화면 확인 스크립트(`scripts/e2e_pair/phone_*.mjs`)로 눈으로 확인.
