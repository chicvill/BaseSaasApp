- 달라지는 것(임차인은 "읽기 + 알림성 쓰기"만 열면 됐지만, 임대인은 **읽기 자체에 민감 정보**가 많다):
  1. **GET도 차단 목록이 필요**하다. 임대인 GET에는 `ledger/export-csv`(입주자 이름 전체), `tax/export-*`·`tax/invoice-register`·`tax/summary`(세무), `contracts/{id}/photo`(계약서 사진), 중개문자 해석 등이 있다. 임차인은 "GET 전부 허용"이었지만 임대인은 **허용 목록(allow-list) 방식**으로 뒤집는다(목록에 없으면 PIN 토큰은 GET도 403).
  2. 계정 모델: `Tenant`에만 있는 `pin_hash`·`quick_devices`를 `Lessor`에도 두거나, 공통 믹스인으로 뺀다. `quicklogin.eligible()`은 "ACTIVE + 호실 있음" 대신 "Lessor + 계정 정상"으로 역할별 분기. `pin_guard`의 `Tenant.get(...)` 조회도 `c["r"]`(역할)에 따라 임차인/임대인 분기.
  3. **토큰 수명은 임차인(3시간)보다 짧게 1시간.** 임대인이 쓰는 업무 앱이 대부분 몇 분 사용이라 불편이 적다.
  4. **기기 수 상한 2대**(임차인은 제한 없음 또는 더 넉넉). 분실 폰은 임대인 ☰ 메뉴의 "바로가기 해제"와 관리인 지원 입장에서 즉시 해제.
  5. 설정은 **일반 로그인 상태에서만** 가능(`PIN_WRITE_ALLOW`에 `/shortcut/*` 없음 — 임차인과 동일). 관리인 대리 접속(`admin_proxy_guard`, 보기 전용)에서는 임대인 PIN 생성 불가.

### B. 허용 범위(3단계, 기본은 1단계만)

| 단계 | 내용 | 라우트 |
|---|---|---|
| **1단계 (PIN 기본)** | 조회 + 소통 + 단순 처리 | GET: `/status`, `/dashboard`, `/messages/rooms`, `/messages/rooms/{no}` · POST: `/chats`(임차인 메시지), `/tickets/{id}/assign`, `/tickets/{id}/complete`, `/auth/logout` |
| **2단계 (기기별 선택 "수납 허용", 기본 꺼짐)** | **장부에 더하기만** 하는 수납. 켤 때 비밀번호 재확인 | POST: `/payments/sms-paste`(미리보기/확인 포함), `/payments/collect`, `/transfer-notices/{id}/confirm`·`/reject` |
| **항상 차단 (일반 로그인 필요)** | 고치기·지우기·돈 밖으로·법적/세무·설정 | `/payments/edit`·`/payments/delete`, `/contracts/*`, `/building/*`, `/rooms/*`·`doorlock`·`release-keys`, `/ledger/export-csv`·`/ledger/import/*`, `/tax/*`·`/outlays/*`, `/checkout/*`, `/expiry/*`, `/billing-notices/*`(일괄 발송), `/tenant-invite`, `/tenant-shortcuts/revoke-all`, `/franchise/*` |

- 2단계를 따로 두는 이유: 임대인 첫 화면의 핵심 업무가 "은행 문자 → 수납"이라, PIN으로 열어도 수납을 못 하면 "PIN으로 들어와 결국 비밀번호를 또 치는" 일이 잦아 PIN의 의미가 줄어든다. 반면 수납은 **추가만 가능하고 수정·삭제는 못 하며**(삭제는 일반 로그인), 잘못 들어간 건은 비밀번호 로그인으로 지울 수 있다.
- 2단계 안전장치(제안): PIN으로 수납할 때 기록(`app_source`·`_events.jsonl`)에 `via_pin`과 기기 id를 남기고, 화면에 "간편 비밀번호로 처리됨" 표시. 하루 PIN 수납 건수·합계 상한(예: 20건/500만 원)을 두는 안은 Gemini 의견을 받고 정한다.
- `billing-notices` 일괄 발송, `tenant-shortcuts/revoke-all`은 "분실 폰 상대가 임차인들에게 영향을 줄 수 있는 행위"라 차단. (분실 대응은 임대인 본인 기기 해제로 충분)

### C. 화면·동선

- 임대인 ☰ 서랍: "📲 바로가기·간편 비밀번호" (임차인 `btnShortcut`과 같은 모달 재사용) — PIN 설정, 이 기기 등록/해제, 기기 목록, **"수납도 PIN으로 허용" 토글**(켤 때 비밀번호 입력).

- PIN 상태에서 차단된 버튼은 **미리 비활성화 + 안내** (`R3Shell.isViaPin()` — 임차인 쪽에 이미 있음). 눌러서 403 보는 것보다 "🔒 아이디·비밀번호 로그인 필요 [다시 로그인]" 한 줄.
- 홈 화면 아이콘: 임대인용 manifest(`/rent3_lessor/` start_url, 이름 "집주인 바로가기"), 임차인과 다른 아이콘 색.
- 계약 방(`rent3_contract`)은 임대인 PIN에서도 **읽기 전용**(임차인과 동일 정책).

### D. 구현 순서(작은 커밋 5개, 단계마다 전체 시험)

1. **모델·인증 일반화**: `Lessor`에 PIN 필드, `quicklogin`/`pool_hub /shortcut/*`/`pin-login`을 역할(tenant/lessor) 대응으로. 임차인 동작·시험은 그대로 통과해야 한다(회귀 방지).
2. **`pin_guard` 역할 분기**: 임대인은 "허용 목록 방식"(GET 포함) + 토큰 1시간 + 기기 2대 상한 + `pay_ok` 기기 플래그(2단계).

### E. 위험·열린 문제

- **허용 목록 누락 위험**: 새 임대인 API를 추가할 때 PIN 목록에 안 넣으면 자동으로 막히므로(안전한 쪽 실패) OK. 반대로 차단 목록 방식이면 새 API가 자동으로 열리는 위험 → 허용 목록 채택 근거.
- 임대인이 여러 건물 계정을 쓰면 계정별 PIN(임차인과 달리 "건물 바꾸기" 개념 없음, 다른 id로 로그인 정책 유지).
- 폰을 잠금화면 없이 두는 사용자는 PIN이 4자리여도 의미가 줄어든다 → 설정 모달에 "폰 잠금(생체/패턴)을 켜 두세요" 안내.
- PIN 토큰 로그인 후 서버 재시작 시 토큰 비밀키(`BASS_SECRET`) 고정 필요(이미 운영 점검표에 있음).
